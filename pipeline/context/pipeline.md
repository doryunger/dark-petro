# Tile pipeline

## sync.py
- The monitor's worker rewrites `sts/<date>/<hot_spot>/<source>.parquet` in place (merge, `If-Match` on the ETag). A changed ETag is therefore the only "delta" signal; there are no new files per publish.
- The ETag stored in `state.json` is the one returned by `get_object`, not the one from the listing: the file can be rewritten between list and get, and the stored value must describe the bytes on disk.
- Captures are write-once (the file name carries the finding id and AIS names), so they are fetched only when missing and pruned when no finding references them.

## build.py
- Build id is `<utc stamp>-<first 12 of input hash>`. The hash covers every (S3 key, ETag) pair plus `SCHEMA_VERSION`; identical inputs never build twice.
- `current` is a relative symlink replaced with `os.replace`, so a reader sees the old build or the new one, never a mix. The proxy mounts the data dir read-only; the relative target resolves inside the mount.
- Capture paths (`capture_png`) are S3 keys (`captures/...`), mirrored as-is under `mirror/` and served under `/captures/`.
- DuckDB reads the Parquets with `union_by_name`: files differ in schema (columns that are all null in one file are typed differently in another). Pinned to 2.0.0 (the Python API dropped `fetch_arrow_table`; `to_arrow_table` replaces it). `ST_AsMVT`, `ST_AsMVTGeom` and `ST_TileEnvelope` exist in 2.0.0: a 1000-point tile with a date filter took 3-4 ms in memory on a laptop, 7-31 KB per tile.
- An empty row set never replaces a live build (`skipped_empty`): an empty listing is far more likely an S3 or credentials problem than real.

## features.py
- No tile layers any more: the PMTiles file and tippecanoe were dropped because DuckDB cuts MVT tiles from the Parquet on request, so there is nothing to keep in step with a prebuilt file. The trade is no static fallback if the service is down.
- `INTERNAL_COLUMNS` (job, attempt, review folder, code and rules versions, run, scene, hull ids) are dropped from `findings.parquet` because the viewer is public and they name internal storage. They stay in the S3 Parquets.
- `SCHEMA_VERSION` is part of the build hash. Bump it whenever the published Parquet changes, otherwise unchanged S3 inputs would skip the rebuild.
- `finding_id` is unique across the product; if a merge ever leaves two rows, the row from the most recently written file wins.

## Query service (design, not built yet)
- Python with DuckDB 2.0; DuckDB does the heavy work, so the language is only HTTP. Go was considered and left out: `go-duckdb` support for 2.0 is unverified and needs cgo.
- One endpoint, `/tiles/{z}/{x}/{y}.mvt`, with the filters (`date` range and `source`, which can hold several values such as `s1,s2`; later more) in the query string; no filters means every finding. The app has no JSON endpoint: the list is built from what the map shows (`queryRenderedFeatures` on the tile layer), so the list and the map are the same rows by construction. Filters are always bound as DuckDB parameters.
- Everything the list or a detail view shows has to be a tile attribute, since tiles are the only data the app receives. The app dedupes by `id` because a feature can come back from two tiles.
- A tile is one query per `z/x/y`. Running the filter once and cutting every tile from a saved result (keyed by the normalised filters plus the build id, with an idle timeout, a cap on how many are held on the 2 GB shared server, and expiry on a new build) is an optimisation to add only if the per-tile cost shows up in measurements.
- A second small endpoint, `/metadata`, returns what the app needs once at start: the time range of the data (the date slider's limits) and the list of sources (the picker's options). It has no counts, because the hot-spot counts in the global view come from the rendered features and so follow the current filters. The app does not fetch it again and does not poll; there is no timer and no SSE.
- Tiles are sent with `Cache-Control: no-cache` and an `ETag` made from the build id and the request parameters, so a browser revalidates and gets a cheap 304 when nothing changed and the new tile after a rebuild. The tile URL carries no build id.
- Filters are validated before they reach the query: dates must match `YYYY-MM-DD`, `source` must be one of the known values, anything unknown is a 400. An empty tile is a valid empty response. DuckDB runs with a `memory_limit` and a thread cap because the server is shared. The tile source sets `maxzoom` 14 so the map overzooms past it instead of requesting tiles the service need not cut.
- Dates are UTC everywhere, including "last week" at start and the slider labels. They are shown as `DD.MM.YYYY` (for example `01.09.2026`); the `date` tile attribute and the filter parameters stay `YYYY-MM-DD`.
- One tile layer, `pairs`, one point per finding; there are no `vessels` or `links` layers. The app draws a two-vessel icon at the pair position: two identical silhouette hulls side by side, a pointed bow and a blunt stern like the ships in the capture image, drawn at yaw 0 with both bows pointing south (`frontend/icons/sts-pair.svg`). The map rotates it with `icon-rotate: ["get", "yaw"]` and `icon-rotation-alignment: map`, so the angle is measured from north.
- The icon is not a fixed file: the frontend has an SVG creator function that takes parameters such as the colour and the base orientation and returns the SVG for them. A symbol layer cannot use an SVG directly, so when the map loads the app builds one image per colour (the SVG through an `Image` with explicit size, at 2x or 3x pixel ratio) and registers each with `map.addImage`; nothing is redrawn while the app runs. There are three colours, and a colour applies to both hulls of a pair: yellow (`#f2c230`, blue was dropped because it is too close to the ocean colour) when sanctioned is false or unknown, red (`#d64545`) when either vessel is sanctioned, i.e. when the tile attribute `sanctioned` is true. The style picks the image with `icon-image: ["case", ["get", "sanctioned"], "pair-sanctioned", "pair"]`. Per-pair rotation is not done by redrawing: it stays in the style, driven by `yaw`. On the map the icons carry an outline so they stay visible on any basemap: black around yellow and red, white around the cyan selected pair (cyan `#4fd0e4`, the third image `pair-selected`); the creator takes the fill and the stroke as parameters. The icons in the reel and the details panel have no outline.
- `yaw` is the axis of the pair: the initial bearing from vessel 1 to vessel 2 plus 90°, wrapped to 0-360 (the icon points south at yaw 0, so this is the bearing minus 90° plus 180°), computed by the pipeline from the two positions and written to `findings.parquet` once per build. It is empty when either position is missing, and the icon then keeps its default rotation. The Parquets carry no heading, course or speed for the vessels, so this is the axis of the pair only: which end is the bow is unknown, the icon may be flipped 180°, and that is accepted. Real headings exist upstream (AIS heading, the imagery hull axis) but are not published in the findings.
- Tile attributes: `id`, `date` (UTC `YYYY-MM-DD`, compares as a string, so no separate day integer), `t` (epoch s), `hot_spot`, `source`, `sanctioned`, `image` (the raw capture PNG key under `/captures/`; the markers image is not used), and, for each of the two vessels, `v1_*` and `v2_*`: name, flag, sanctioned (so the panel can label the right vessel) and IMO when known (the MMSI is not published); also `yaw`. The pair-level `sanctioned` (true if either vessel is) stays for the icon colour. `verdict`, `qa_status`, `named`, `ais_covered` and `length_m` are not tile attributes. Location is the geometry.
- There is no clustering for now. The tiles carry every finding at every zoom and the map draws all of them, with no limit and no hiding; if the map gets cluttered, narrowing the filters is the user's job. Clustering is parked, not dropped: it still makes sense and needs refining before it is built. The idea, as far as it was designed: the app groups the pairs in view into clusters in the list only (never in the MVT), each tied to an area it draws as a GeoJSON polygon; below zoom 10 the four hot-spot areas, at zoom 10 to 13 four quadrants (NE, SE, SW, NW) cut from the centre of a hot spot, from zoom 14 circles named A, B, C from west to east, each level shown only above a threshold of 20 pairs on the display; clicking a cluster flies to its area. The full wording is in this file at commit `184f24c`.
- The four hot-spot areas stay: their boundaries and names are drawn from `frontend/hot_spots.json` (`fujairah_outer`, `off_sohar`, `malaysia_eopl`, `johor_east_scs`) at every zoom, with no fill logic or counts, whether or not they hold data.
- The hot-spot areas are the monitor's own site rectangles (name plus bounding box, in its `sts_watch` rules). This repo owns a copy of only the names and boxes, never the monitor's explanatory text: `frontend/hot_spots.json`, a GeoJSON polygon per hot spot, copied once from the monitor's rules and edited here from now on. `malaysia_eopl` and `johor_east_scs` touch along one edge.
- Start view: the app fits the four hot-spot boxes with padding for the reel, capped at zoom 4, so that all four are visible whatever the screen width. A fixed zoom 4 centred at about 81.1°E, 13.3°N only shows all four when the map area is about 1250 px wide, which with a reel of about 450 px needs a window wider than about 1700 px.

## Reel and map behaviour (design, frontend not built yet)
- The app is a React app, built with Vite. On start it shows the pairs of the last 7 days ending today (UTC); if no data falls in that week, the slider handles sit at the end of the data's range and the list and the map are empty, with an empty state saying so. The layout is one grid: a header across the full width (title DarkPetro); under it the filters block, which spans the width of the reel and the details panel; under the filters the reel of entries at 15vw and the details panel at 22vw, side by side, running to the bottom of the screen; the map takes the rest of the width (63vw), from under the header to the bottom. The details panel is always there, so the map is never resized when an entry is opened; it shows the opened entry, with its capture image at the panel's width. The filters block holds: a titled "Time range" section with the date range slider, the earliest and latest dates of the data above its two edges and the selected range written under it, then a titled "Source" section with one row holding a checkbox on the left of each source (Sentinel-1, Sentinel-2; both on by default, so several can be selected) and the Filter button at the right end of that row.
- Hovering a pair's icon on the map shows a MapLibre `Popup` (no close button, closed on mouse leave, anchored above the icon with a small offset). Its content is the same card markup as a reel entry (icon, ID, then area, date and source), so it gets the same colours, fonts and structure: the popup uses the card background (`#223c4e`), white text and rounded corners, and the tip has the same colour. The look is a CSS override of `.maplibregl-popup-content` and `.maplibregl-popup-tip`; the page draws the popup with the DOM MapLibre generates (`maplibregl-popup`, `-anchor-bottom`, `-tip`, `-content`). The cursor is a pointer over an icon. Icons are small at low zoom and grow only slightly with it, so they are never huge: `icon-size` is an interpolation on the zoom, starting at 0.3 of the drawing at zoom 4 and below, 0.5 at zoom 10, 0.8 at zoom 14 and 1 at zoom 16 and above (the starting values, to be tuned on the real map).
- The reel is ordered by capture date and time, newest first: sorted on the `t` attribute, descending, with `id` as the tie-break, so the most recent entries are at the top. Above the entries, outside the scrolling area, is a small "Sort by" drop menu with two choices, Latest (the default) and Oldest (`t` ascending); it only changes the order of the list, not the map or the filters. The icons on the map are drawn in the same order: a `symbol-sort-key` of `t` for Latest or `-t` for Oldest (a higher key is drawn on top), changed with `setLayoutProperty` when the sort changes, so the entry at the top of the reel is the icon on top, and the selected pair is drawn above all. Icons use `icon-allow-overlap` and `icon-ignore-placement`, so none is hidden.
- An entry is a rounded card a little brighter than the layout, with white text, in two rows. Row one: a small pair icon (the same SVG, drawn through a CSS mask so one file serves both colours: yellow, red when sanctioned) turned 90° clockwise, so the hulls lie one above the other with the bows pointing left, and next to it the ID, a bit bigger and in medium weight. Row two, under both, smaller and in italic: the area at the left, then the capture date and the source (S1 or S2, the `source` attribute in capitals) at the right. The opened entry is bright cyan with dark blue text and a dark icon, so it stands out from the others. The reel and the details panel share one minimalist scrollbar (thin thumb in the map's blue, no arrows, transparent track), so all scrolling components look the same. A CSS mask only loads over http, not from a `file://` page, so the page has to be served to be checked. The ID shown, in the reel and in the panel header, is the published `id` (`<source>_<capture time>_<hull id>`) without its first two parts, that is everything after the second underscore, for example `55982-271906`, which is the hull id; it is the same ID in both places. `hull_id` is in `INTERNAL_COLUMNS` and is dropped from the Parquet, but it is part of `id` and so is already public in every tile; showing it in the reel was accepted.
- The details panel has its own header bar at the top, small and fixed: it does not move when the content below it scrolls (only the image and the grid scroll). It holds the pair icon (turned 90° like in the reel, red when sanctioned), the ID and, at the right end, a small close (x) button (a bright red cross, `#ff5c5c`, with a dark outline), then the capture image with a small muted caption under it ("Source: Sentinel-1" or "Source: Sentinel-2"; the source is not a row of the grid), then a grid with no column headers: a muted label on the left, the value on the right, with a border only under each row. Rows: Vessel 1 and Vessel 2 (name, flag, a red "Sanctioned" label next to the name when that vessel is sanctioned, and a small muted "IMO 1234567" line under the name when the IMO is known; the label wraps under the name when the row is short), then Date, Time (UTC), Area and Position (lat, lon from the pair's geometry). The filters block is 149 px high, which leaves the reel and the details panel 46 px more than before. The content then fits at 1440x900, 1536x864 and 1920x1080, and is about 107% of the panel height at 1366x768 (568 px against 531 px), so only the smallest laptop screens scroll the panel.
- Clicking an entry in the reel opens it in the details panel (one at a time), highlights it in the reel and, when the zoom is 13 or lower, flies the map to the pair at zoom 15 (the tile source stops at zoom 14, so the map overzooms its tiles there). Above zoom 13 it does not fly, so a user who has already zoomed in keeps the view they have; the same rule applies to a click on an icon on the map. Selecting a pair never changes the extent in any other case. Clicking a pair's icon on the map opens its entry in the details panel and scrolls the reel to it, with the same fly rule. The pair's icon on the map turns cyan (a third image, `pair-selected`, chosen by an `icon-image` expression that compares the pair `id` with the selected id) so it is easy to find; the other pairs keep yellow and red. The selection stays until the user picks another pair or presses the close button: the list follows the viewport and may no longer contain the selected pair, but the panel and the cyan icon stay on it. Close clears the selection (the panel is empty again, the icon returns to its colour) and does not move the map. There is no Show on map button.
- The only filters are the date range and the source. `sanctioned` is shown on the entry itself and is not a filter control.
- Query area: the list is always built from the features in the current viewport (every pair in it) and is never locked, at any zoom. While the zoom is 13 or lower the viewport is also stored as the query area after each move; only the last one is kept. Above zoom 13 the stored area is left as it was and a "Back to query area" button appears at the bottom centre of the map (dark blue with white text); it flies to the stored bounds and disappears again once the zoom is 13 or lower. After flying to a pair the list therefore shows only the pairs in that small viewport, and the way back to the wider list is that button. The user can pan freely at every zoom.
- Basemap: the Mapbox satellite style (the labelled variant, `satellite-streets-v12`, is the working choice, so that places and borders can be read; the plain `satellite-v9` is the alternative), used through MapLibre (Mapbox's documentation describes MapLibre as working with its tile APIs; the use is personal and the terms were accepted by Dor, not checked here). It needs an access token. A public token (`pk.`) is visible in the browser by design, so only a public token is ever used, never a secret one (`sk.`), and it is restricted to the viewer's address in the Mapbox account. Nothing credential-like is committed: the token lives in the git-ignored `frontend/.env.local` (read by the bundler as `VITE_MAPBOX_TOKEN`), and the repo holds only a placeholder `frontend/.env.example`. The style is requested through its https URL with the token and has to be checked to render in MapLibre. Satellite imagery is darker and busier than the flat placeholder colour, which is why the icons carry outlines; the hot-spot outline colour has to be chosen on the real imagery. Visitors' requests, including their IP addresses, go to Mapbox, usage is billed or capped by the Mapbox plan, and the Mapbox and OpenStreetMap attribution is shown.
- Rotation and tilt are blocked (drag and touch rotation off, keyboard rotation off, `maxPitch` 0). The map is not enabled for touch: the viewer is for a mouse and keyboard, so the hover popup needs no touch variant.
- Map controls stay, restyled in the dark theme: the navigation control with zoom in and out (no compass, since rotation is off), the scale bar at the bottom left and the attribution at the bottom right.
- When Filter is pressed, a selected pair whose `date` or `source` falls outside the new filter is dropped: the details panel closes and the cyan icon goes. The app can decide this from the selected pair's own attributes, without querying.
- Errors (a tile request or `/metadata` failing) show in a toast at the top centre of the map, in the dark theme with a red accent and a close (x) button, and go away by themselves after a few seconds.
- The zoom threshold 13 is compared with `map.getZoom()` as it is, fractional (anything above 13.0, never a rounded integer). It applies to the Back to query area button, to the stored query area and to the fly rule.

## listen.py
- Waits on the SQS queue that S3 notifies. One build per burst: the worker writes several Parquets per job, so collection continues until the queue has been quiet for `SETTLE_S` (10 s), never longer than `SETTLE_MAX_S` (60 s). `WAIT_S` is the SQS long-poll maximum (20 s).
- Messages are deleted only after the run succeeded; a failed run leaves them for redelivery, and the queue's redrive policy moves them to the dead-letter queue after 5 receives. Test events and keys outside `sts/*.parquet` are deleted immediately.
- SIGTERM is handled explicitly: the process is PID 1 in its container and would otherwise ignore it.
- A peek at the queue with `VisibilityTimeout=0` still counts as a receive; five of them send a message to the dead-letter queue.

## __main__.py
- `run` syncs from S3 and builds if anything changed, `build` rebuilds from the local mirror only, `listen` runs on S3 events.
- A file lock in the data dir keeps the listener and the hourly timer off the data at the same time. The timer only reconciles in case an event was missed.
