# Tile pipeline

## sync.py
- The monitor's worker rewrites `sts/<date>/<hot_spot>/<source>.parquet` in place (merge, `If-Match` on the ETag). A changed ETag is therefore the only "delta" signal; there are no new files per publish.
- The ETag stored in `state.json` is the one returned by `get_object`, not the one from the listing: the file can be rewritten between list and get, and the stored value must describe the bytes on disk.
- Captures are compared by S3 ETag (one listing of `captures/`, stored in `captures_state.json`), because the monitor replaced every image in place under the same key once (the numbered markers are now drawn on the capture itself) and a fetch-only-when-missing rule kept serving the old pictures. A run that finds the Parquets unchanged still refreshes the captures on disk. Captures are pruned when no finding references them.

## Sanctioned vessels
- `sanctioned/<date>/<hot_spot>/<source>.parquet` has the same layout as `sts/` but one row per single vessel: `vessel_*` columns (no `vessel_1_`/`vessel_2_`), `verdict = single`, the detection position in `lat`/`lon` (`vessel_lat`/`vessel_lon` is the AIS-matched position and is not published). Both prefixes go through one sync, one input hash and one build, so a change under either rebuilds both tables; `sync_parquets` takes both prefixes together because the state file is shared and a per-prefix call would drop the other prefix's keys as "gone from S3".
- `sanctioned.parquet` is an allow-list like `findings.parquet` (`SANCTIONED_TYPES` in `build.py`): id, position, capture time, hot spot, source, capture image, `yaw` and the vessel's name, flag and IMO. Sanctions lists, programs, match scores and AIS details stay out. It is always written, empty if need be, so the tile query never meets a missing file; a build from before the tab has no such file and the service answers an empty tile.
- `yaw` is the monitor's `heading_deg` for the vessel, rotated like the pairs (`F.rotation`); a vessel without one has no `yaw` and the map draws it upright. The pair-axis fallback does not apply to a single vessel.
- A build is skipped as empty only when both tables are empty. `rejected` findings are hidden the same way as for pairs and the manifest has a `sanctioned` block with the same counts as the top level.
- The S3 notification that feeds the queue has to include the `sanctioned/` prefix for the listener to react to a publish there; until then the hourly timer picks the files up.

## build.py
- Build id is `<utc stamp>-<first 12 of input hash>`. The hash covers the SHA-256 of every mirrored Parquet plus `SCHEMA_VERSION`, so it follows the files on disk, not the S3 ETag; identical inputs never build twice and a file changed or dropped into the mirror by any means triggers a rebuild.
- `current` is a relative symlink replaced with `os.replace`, so a reader sees the old build or the new one, never a mix. The proxy mounts the data dir read-only; the relative target resolves inside the mount.
- Capture paths (`capture_png`) are S3 keys (`captures/...`), mirrored as-is under `mirror/` and served under `/captures/`.
- DuckDB reads the Parquets with `union_by_name`: files differ in schema (columns that are all null in one file are typed differently in another). Pinned to 2.0.0 (the Python API dropped `fetch_arrow_table`; `to_arrow_table` replaces it). `ST_AsMVT`, `ST_AsMVTGeom` and `ST_TileEnvelope` exist in 2.0.0: a 1000-point tile with a date filter took 3-4 ms in memory on a laptop, 7-31 KB per tile.
- An empty row set never replaces a live build (`skipped_empty`): an empty listing is far more likely an S3 or credentials problem than real.

## features.py
- No tile layers any more: the PMTiles file and tippecanoe were dropped because DuckDB cuts MVT tiles from the Parquet on request, so there is nothing to keep in step with a prebuilt file. The trade is no static fallback if the service is down.
- `findings.parquet` is an allow-list (`TABLE_TYPES` in `build.py`): only the columns the tiles read are written, and everything else in the S3 Parquets is left out, because the file is public and storing more than the viewer uses is redundant. Nothing is hidden by a block-list; a column reaches the public only when someone adds it to the list.
- A finding with `qa_status = 'rejected'` is hidden: the build drops it after the duplicates are merged (`visible` in `features.py`), so it is in neither `findings.parquet` nor the tiles, its capture is no longer referenced and is pruned, and the manifest counts leave it out. The merge comes first because the newest row of a `finding_id` decides: a pair published as confirmed and rejected later disappears at the next build, and a rejection later overturned (for example to `corrected`) brings it back. `qa_status` itself is not published. `unreviewed`, `confirmed`, `corrected` and a missing status all stay visible. If every finding were rejected the live build is kept (`skipped_empty`), because an empty table would also leave the app without a date range.
- `SCHEMA_VERSION` is part of the build hash. Bump it whenever the published Parquet changes, otherwise unchanged S3 inputs would skip the rebuild.
- `finding_id` is unique across the product; if a merge ever leaves two rows, the row from the most recently written file wins.
- `yaw` is the icon rotation written to `findings.parquet`. It is the monitor's published `heading_deg` (the axis of the hulls as an angle from north, 0 to 180, so which end is the bow is unknown and the icon may be flipped 180°; `heading_source` says `ai2` or `fitted`, and neither column is published). The icon is drawn with its hulls running north-south at yaw 0, so the heading is used as it is. A finding with no heading falls back to the old estimate: the initial bearing from vessel 1 to vessel 2 plus 90°, wrapped to 0-360, which assumes the ships lie side by side and was visibly wrong for pairs whose AIS positions lie along the hulls; it is empty when either position is missing.
- `findings.parquet` has fixed types for those columns (`TABLE_TYPES` in `build.py`): a column missing from every input is added as nulls, and a column the inputs type differently (for example an IMO that is a number in one file and text in another) is cast, so the tile query never meets a surprise.

## serve.py
- Python with DuckDB 2.0; DuckDB does the heavy work, so the language is only HTTP. Go was considered and left out: `go-duckdb` support for 2.0 is unverified and needs cgo. The server is the standard library's threaded HTTP server.
- One service answers everything the viewer needs, so the proxy has one upstream (the service's loopback port): `/tiles/{z}/{x}/{y}.mvt`, `/metadata`, `/captures/...` (the mirrored PNGs, sent with an ETag from the file's mtime and size and `no-cache`, so a replaced image shows up on the next load and an unchanged one costs a 304, resolved inside `mirror/captures` so a path cannot leave it) and the built React app (`index.html` is never cached, hashed assets are; unknown paths without a dot fall back to `index.html`). The proxy config lives on the server, outside this repo, and has not been looked at.
- A tile is one DuckDB query per `z/x/y` on `current/findings.parquet` (about 4 ms for 1000 features in memory), cut with `ST_AsMVT`, `ST_AsMVTGeom` and `ST_TileEnvelope` into one layer, `pairs`, one point per finding. A lon/lat box 10% wider than the tile limits the rows first. `ST_AsMVT` supports only VARCHAR, FLOAT, DOUBLE, INTEGER, BIGINT and BOOLEAN properties, and leaves out NULL ones, which is how "IMO when known" works. A feature near a tile edge is in both tiles (the buffer), so the app dedupes by `id`. An empty tile is a valid tile with no features.
- Sanctioned vessels are a second layer, `sanctioned`, at `/tiles/sanctioned/{z}/{x}/{y}.mvt`, built from `sanctioned.parquet` with the same filters. A vessel is one point: only its newest detection under the filters is in the tile (`head_rank = 1`, ranked by capture time then ID over all rows that pass the date and source filters, before the tile bounds cut anything, so the head is the same wherever the tile is). The attribute `n` is the vessel's number of detections under the same filters, also counted before the bounds. Its other attributes are `id`, `date`, `t`, `hot_spot`, `source`, `image`, `yaw`, `lon`, `lat` and the one vessel as `v1_name`, `v1_flag`, `v1_imo`, so the app reads a vessel with the same code as the first vessel of a pair. A row without an IMO is its own vessel. There is no `sanctioned` flag: everything in it is. The date range and the source list in `/metadata` and the source check on `source` cover both datasets, so one slider and one source picker serve both tabs.
- `/tiles/activity/{z}/{x}/{y}.mvt?from=...&to=...&id=...` serves the one selected suspicious-activity finding as a temporary MVT overlay. It reads `findings.parquet`, requires the exact finding ID and applies only the date range, not source filters. The frontend mounts it alongside the sanctioned layer while the activity detail is open, then removes the source and its cached tiles when the detail closes.
- `/tracks/<imo>` returns `{imo, points}` for the sanctioned vessel with that IMO, newest first, every detection (the newest too) under the same `from`/`to`/`source` filters (`filter_clause`, shared with the tiles) and the same validation. Each point has what the details panel and the history list show: `id`, `date`, `t`, `hot_spot`, `source`, `image`, `yaw`, `lon`, `lat`, `name`, `flag`, `imo`. An unknown IMO or a build without `sanctioned.parquet` gives an empty list. It exists because the tile carries only the newest detection of each vessel. The IMO is already a tile attribute (`v1_imo`), so it publishes nothing new. Sent `no-cache`, no ETag: a few rows, and a rebuild must show at once.
- `/activities/<imo>` returns `{imo, activities}` for pair findings where either published vessel IMO exactly matches the sanctioned vessel. It uses the active `from`/`to` date range and deliberately ignores source filters, so a documented match remains reachable when its source checkbox is off. Each result carries the pair detail fields and `matched_vessel` (`1` or `2`); rejected findings are already absent from `findings.parquet`. It exists to link a vessel to documented suspicious activity without publishing extra columns. An unknown IMO or a build without `findings.parquet` gives an empty list. Sent `no-cache`, no ETag.
- `/activity-imos` returns the distinct sanctioned vessel IMOs with at least one exact pair IMO match under the active `from`/`to` date range. Source filters are not accepted or applied. The viewer uses this small lookup to mark vessel cards that have related activities; it adds no published Parquet columns. Sent `no-cache`, no ETag.
- Tile attributes (pairs): `id`, `date` (UTC `YYYY-MM-DD`, compares as a string, so no separate day integer), `t` (epoch s), `hot_spot`, `source`, `sanctioned`, `image` (the capture PNG key under `/captures/`; the monitor draws the numbered vessel markers, 1 and 2, on the image itself, so there is no separate markers file), the exact `lon` and `lat` (the tile geometry is only as accurate as the tile's zoom, about a kilometre at zoom 3, which would put a pair 100 pixels off the centre after a fly to zoom 15 and show a wrong position), and, for each of the two vessels, `v1_*` and `v2_*`: name, flag, sanctioned (so the panel can label the right vessel) and IMO when known (the MMSI is not published); also `yaw`. The pair-level `sanctioned` (true if either vessel is) stays for the icon colour. `verdict`, `qa_status`, `named`, `ais_covered` and `length_m` are not tile attributes. Location is the geometry.
- No JSON endpoint for the list: the app builds the list from the features the map has rendered, so the list and the map are the same rows. Everything the list or the panel shows has to be a tile attribute.
- The filters are `from` and `to` (`YYYY-MM-DD`, UTC, both ends inclusive) and `source` (a comma list such as `s1,s2`); none means everything. They are validated before they reach the query and bound as DuckDB parameters: a date must match the pattern and be a real date, `from` must not be after `to`, `source` must be one the manifest knows, an unknown or repeated parameter, a zoom above 14 or a tile outside the grid is a 400.
- Tiles are sent with `Cache-Control: no-cache` and an `ETag` made from `TILE_REVISION`, the build id, the path and the sorted parameters, so a browser revalidates and gets a cheap 304 when nothing changed and the new tile after a rebuild; the tile URL carries no build id. `TILE_REVISION` (in `serve.py`) must be bumped whenever the tile's content or attributes change without a new data build: the build id follows the S3 inputs only, so after the tile query changed a browser kept a cached old tile and got a 304 for it (the reel showed a vessel once per detection, without the badge).
- `/metadata` returns what the app needs once at start, from `manifest.json`: `min_date` and `max_date` (the data's time range, the date slider's limits) and `sources` (the picker's options). No counts, because the counts in the app come from the rendered features and so follow the current filters. The app does not fetch it again and does not poll; there is no timer and no SSE.
- Running filtered tiles from a saved result (one filter query, keyed by the normalised filters plus the build id, with an idle timeout and a cap on how many are held on the 2 GB shared server) was considered and left as an optimisation to add only if the per-tile cost shows up in measurements.
- Memory: DuckDB runs with `memory_limit` 200 MB (`STS_DUCKDB_MEMORY`) and 2 threads; compose caps the container at 320 MB, mounts `data/` read-only, has a read-only root file system (the built app is inside the image, not mounted) and no AWS keys. The spatial extension is installed into `/opt/duckdb-extensions` when the image is built, so nothing is downloaded at run time; the viewer unit is the only thing `deploy.sh` restarts for the viewer, besides the listener it already restarted.
- The port is `STS_PORT` inside the container (8080); compose publishes it on the server's loopback only, at the port given by `VIEWER_PORT` in the git-ignored `deploy/deploy.env`.

## listen.py
- Waits on the SQS queue that S3 notifies. One build per burst: the worker writes several Parquets per job, so collection continues until the queue has been quiet for `SETTLE_S` (10 s), never longer than `SETTLE_MAX_S` (60 s). `WAIT_S` is the SQS long-poll maximum (20 s).
- Messages are deleted only after the run succeeded; a failed run leaves them for redelivery, and the queue's redrive policy moves them to the dead-letter queue after 5 receives. Test events and keys outside `sts/*.parquet` are deleted immediately.
- SIGTERM is handled explicitly: the process is PID 1 in its container and would otherwise ignore it.
- A peek at the queue with `VisibilityTimeout=0` still counts as a receive; five of them send a message to the dead-letter queue.

## __main__.py
- `run` syncs from S3 and builds if anything changed, `build` rebuilds from the local mirror only, `watch` does that whenever the mirror changes, `listen` runs on S3 events, `serve` runs the viewer service (it does not touch S3 and needs no AWS keys).
- `watch` polls the mirror's (path, size, mtime) every `STS_WATCH_S` (5 s), waits for one more poll to see it unchanged, then runs an offline build; the hash makes a no-change run a no-op. It needs no AWS keys.
- A file lock in the data dir keeps the listener and the hourly timer off the data at the same time. The timer only reconciles in case an event was missed.
