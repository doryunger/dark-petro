# Tile pipeline

## sync.py
- The monitor's worker rewrites `sts/<date>/<hot_spot>/<source>.parquet` in place (merge, `If-Match` on the ETag). A changed ETag is therefore the only "delta" signal; there are no new files per publish.
- The ETag stored in `state.json` is the one returned by `get_object`, not the one from the listing: the file can be rewritten between list and get, and the stored value must describe the bytes on disk.
- Captures are write-once (the file name carries the finding id and AIS names), so they are fetched only when missing and pruned when no finding references them.

## build.py
- Build id is `<utc stamp>-<first 12 of input hash>`. The hash covers every (S3 key, ETag) pair plus `SCHEMA_VERSION`; identical inputs never build twice.
- `current` is a relative symlink replaced with `os.replace`, so a reader sees the old build or the new one, never a mix. The proxy mounts the data dir read-only; the relative target resolves inside the mount.
- Capture paths (`capture_png`) are S3 keys (`captures/...`), mirrored as-is under `mirror/` and served under `/captures/`.
- DuckDB reads the Parquets with `union_by_name`: files differ in schema (columns that are all null in one file are typed differently in another). Pinned to 2.0.0 (the Python API dropped `fetch_arrow_table`; `to_arrow_table` replaces it). `ST_AsMVT`, `ST_AsMVTGeom` and `ST_TileEnvelope` exist in 2.0.0: a 1000-point tile with a date filter took 3-4 ms in memory on a laptop, 7-31 KB per tile.
- An empty row set never replaces a live build (`skipped_empty`): an empty listing is far more likely an S3 or credentials problem than real.

## features.py
- No tile layers any more: the PMTiles file and tippecanoe were dropped because DuckDB cuts MVT tiles from the Parquet on request, so there is nothing to keep in step with a prebuilt file. The trade is no static fallback if the service is down.
- `INTERNAL_COLUMNS` (job, attempt, review folder, code and rules versions, run, scene, hull ids) are dropped from `findings.parquet` because the viewer is public and they name internal storage. They stay in the S3 Parquets.
- `SCHEMA_VERSION` is part of the build hash. Bump it whenever the published Parquet changes, otherwise unchanged S3 inputs would skip the rebuild.
- `finding_id` is unique across the product; if a merge ever leaves two rows, the row from the most recently written file wins.
- `yaw` is the axis of the pair, computed by the build once per run from the two vessel positions and written to `findings.parquet`: the initial bearing from vessel 1 to vessel 2 plus 90°, wrapped to 0-360 (the viewer's icon points south at yaw 0, so this is the bearing minus 90° plus 180°); it is empty when either position is missing. The Parquets carry no heading, course or speed for the vessels, so this is the axis of the pair only: which end is the bow is unknown, the icon may be flipped 180°, and that is accepted. Real headings exist upstream (AIS heading, the imagery hull axis) but are not published in the findings.
- `findings.parquet` has a fixed set of columns the tiles read, with fixed types (`TABLE_TYPES` in `build.py`): a column missing from every input is added as nulls, and a column the inputs type differently (for example an IMO that is a number in one file and text in another) is cast, so the tile query never meets a surprise.

## serve.py
- Python with DuckDB 2.0; DuckDB does the heavy work, so the language is only HTTP. Go was considered and left out: `go-duckdb` support for 2.0 is unverified and needs cgo. The server is the standard library's threaded HTTP server.
- One service answers everything the viewer needs, so the proxy has one upstream (the service's loopback port): `/tiles/{z}/{x}/{y}.mvt`, `/metadata`, `/captures/...` (the mirrored PNGs, immutable and cached for a year because they are write-once, resolved inside `mirror/captures` so a path cannot leave it) and the built React app (`index.html` is never cached, hashed assets are; unknown paths without a dot fall back to `index.html`). The proxy config lives on the server, outside this repo, and has not been looked at.
- A tile is one DuckDB query per `z/x/y` on `current/findings.parquet` (about 4 ms for 1000 features in memory), cut with `ST_AsMVT`, `ST_AsMVTGeom` and `ST_TileEnvelope` into one layer, `pairs`, one point per finding. A lon/lat box 10% wider than the tile limits the rows first. `ST_AsMVT` supports only VARCHAR, FLOAT, DOUBLE, INTEGER, BIGINT and BOOLEAN properties, and leaves out NULL ones, which is how "IMO when known" works. A feature near a tile edge is in both tiles (the buffer), so the app dedupes by `id`. An empty tile is a valid tile with no features.
- Tile attributes: `id`, `date` (UTC `YYYY-MM-DD`, compares as a string, so no separate day integer), `t` (epoch s), `hot_spot`, `source`, `sanctioned`, `image` (the raw capture PNG key under `/captures/`; the markers image is not used), the exact `lon` and `lat` (the tile geometry is only as accurate as the tile's zoom, about a kilometre at zoom 3, which would put a pair 100 pixels off the centre after a fly to zoom 15 and show a wrong position), and, for each of the two vessels, `v1_*` and `v2_*`: name, flag, sanctioned (so the panel can label the right vessel) and IMO when known (the MMSI is not published); also `yaw`. The pair-level `sanctioned` (true if either vessel is) stays for the icon colour. `verdict`, `qa_status`, `named`, `ais_covered` and `length_m` are not tile attributes. Location is the geometry.
- No JSON endpoint for the list: the app builds the list from the features the map has rendered, so the list and the map are the same rows. Everything the list or the panel shows has to be a tile attribute.
- The filters are `from` and `to` (`YYYY-MM-DD`, UTC, both ends inclusive) and `source` (a comma list such as `s1,s2`); none means everything. They are validated before they reach the query and bound as DuckDB parameters: a date must match the pattern and be a real date, `from` must not be after `to`, `source` must be one the manifest knows, an unknown or repeated parameter, a zoom above 14 or a tile outside the grid is a 400.
- Tiles are sent with `Cache-Control: no-cache` and an `ETag` made from the build id, the path and the sorted parameters, so a browser revalidates and gets a cheap 304 when nothing changed and the new tile after a rebuild; the tile URL carries no build id.
- `/metadata` returns what the app needs once at start, from `manifest.json`: `min_date` and `max_date` (the data's time range, the date slider's limits) and `sources` (the picker's options). No counts, because the counts in the app come from the rendered features and so follow the current filters. The app does not fetch it again and does not poll; there is no timer and no SSE.
- Running filtered tiles from a saved result (one filter query, keyed by the normalised filters plus the build id, with an idle timeout and a cap on how many are held on the 2 GB shared server) was considered and left as an optimisation to add only if the per-tile cost shows up in measurements.
- Memory: DuckDB runs with `memory_limit` 200 MB (`STS_DUCKDB_MEMORY`) and 2 threads; the unit caps the container at 320 MB, mounts `data/` read-only, has a read-only root file system and no AWS keys. The spatial extension is installed into `/opt/duckdb-extensions` when the image is built, so nothing is downloaded at run time; the viewer unit is the only thing `deploy.sh` restarts for the viewer, besides the listener it already restarted.
- The port is `STS_PORT` inside the container (8080); the unit publishes it on the server's loopback only, at the port given by `VIEWER_PORT` in the git-ignored `deploy/deploy.env`.

## listen.py
- Waits on the SQS queue that S3 notifies. One build per burst: the worker writes several Parquets per job, so collection continues until the queue has been quiet for `SETTLE_S` (10 s), never longer than `SETTLE_MAX_S` (60 s). `WAIT_S` is the SQS long-poll maximum (20 s).
- Messages are deleted only after the run succeeded; a failed run leaves them for redelivery, and the queue's redrive policy moves them to the dead-letter queue after 5 receives. Test events and keys outside `sts/*.parquet` are deleted immediately.
- SIGTERM is handled explicitly: the process is PID 1 in its container and would otherwise ignore it.
- A peek at the queue with `VisibilityTimeout=0` still counts as a receive; five of them send a message to the dead-letter queue.

## __main__.py
- `run` syncs from S3 and builds if anything changed, `build` rebuilds from the local mirror only, `listen` runs on S3 events, `serve` runs the viewer service (it does not touch S3 and needs no AWS keys).
- A file lock in the data dir keeps the listener and the hourly timer off the data at the same time. The timer only reconciles in case an event was missed.
