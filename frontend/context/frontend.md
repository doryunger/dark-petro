# Frontend

## Stack and files
- Solid 2.0 (`solid-js` and `@solidjs/web`) with Vite 8, Mapbox GL JS 3, Biome, Vitest and TypeScript (strict; every source file is `.ts` or `.tsx`, no `.js` or `.jsx`), in `frontend/`. `npm run check` runs Biome lint, `tsc --noEmit` and the unit tests; the pre-commit hook, GitHub Actions and image build use the same check. `src/lib` holds the logic that has tests (dates, filters, entries, layer expressions, icons, Mapbox addresses, geometry, the virtual list), `src/components` the screen, `src/styles/app.css` the look, `src/data/hot_spots.json` the four areas. `npm run dev` serves the viewer and sends `/tiles`, `/metadata` and `/captures` to the service on the local port set in `vite.config.ts`; `npm test` runs the unit tests; `npm run build` builds into `dist/`.
- The map is Mapbox GL JS 3, not MapLibre: the custom style is built on a Mapbox Standard import (no layers of its own), which MapLibre 6 rejected ("name: unknown property"), so the viewer fell back to the plain background. Mapbox GL JS reads `mapbox://` styles itself, so the address-rewriting code that MapLibre needed is gone. The map is created with `projection: "mercator"` because the Standard style defaults to a globe at low zoom.
- The reel is a fixed-height virtual list (4.375 rem per row, 70 px at the default font size), so thousands of rows cost a few dozen elements. An empty list says "No findings in this view." and a missing capture says "Image not available".
- The list is rebuilt from `queryRenderedFeatures` on the map's `idle` and `moveend` events, deduped by `id`, and only handed to the screen when the set of IDs changed.
- Checked in a real browser (headless Chromium, 29 checks) against the service on synthetic data covering every hot spot: the week's list, the order, the panel, the popup, the fly rule, the list following the extent, the filters, the last source that cannot be unchecked, a selected pair dropped by a filter, close, and the error toast. That script lives outside the repo.

## Layout and the reel
- The slider handles are light grey with a radial gradient, a yellow ring and a 2 px grey ring (`#8b959e`, an inset `box-shadow` in `app.css`) around the light fill, so they stand out from the yellow track without the glare; an outer shadow was tried and looked like a halo.
- The layout background is `#030c13` for the page, the header, the filters, the reel and the details panel, with a 1 px dark navy line (`#091722`) under the header and a 3 px line (`#12293a`) on the right edge of the reel, which divides the reel from the details panel (1 px was too faint to read as a division), and no border on the filters, the sort bar or the details panel; the cards in the reel keep their lighter colour, and the thin lines between the rows of the details grid stay.
- Sizes are relative: the stylesheet uses `rem` for fonts, spacing, radii and component sizes and `vw` for the three columns, and keeps pixels only for hairlines (1 to 4 px borders and outlines, shadows). One `rem` is the browser's root font size (16 px by default), so a larger browser font scales the whole screen, and the stylesheet was checked to render pixel for pixel like the old pixel version at 16 px. The reel's virtual list is the one place where JavaScript needs pixels: its row height and offset are `ROW_HEIGHT_REM` and `ROW_TOP_REM` in `lib/constants.ts`, and `remPx()` in `lib/units.ts` turns them into pixels for the scroll maths.
- The viewer is a Solid app, built with Vite. On start it shows the pairs of the last 10 days ending today (UTC; `DEFAULT_RANGE_DAYS` in `lib/constants.ts`, 7 before 2026-11-25); the slider runs from the earliest date in the data to today (UTC), or to the newest date in the data if that is later (`extendToToday` in `lib/dates.ts`; `/metadata` still returns the data's own range), so a week with no findings shows empty days instead of a slider that stops at the last capture, and the list and the map are empty with an empty state saying so. The layout is one grid: a header across the full width (title Dark Petro); under it the filters block, which spans the width of the reel and the details panel; under the filters the reel of entries at 13vw (at least 13 rem, at most 15 rem) and the details panel at 15vw (at least 15 rem, at most 18 rem; fixed vw widths were cramped at 1366 px and too wide on large screens), side by side, running to the bottom of the screen; the map takes the rest of the width, from under the header to the bottom. The details panel is always there, so the map is never resized when an entry is opened (hiding it while nothing is open would resize the map on every open and close, which fires the map's `idle` and rebuilds the list from the new viewport, and a selected entry can drop out of it); it always has a "Capture details" title and nothing under it while no entry is open (a one-line hint used to be there and was removed); it shows the opened entry, with its capture image as a square, 75% of the panel width, at least 9rem and never wider than the panel's content (a fixed cap looked tiny on wide screens and a full-width image looked too big; the captures are square, so a 4:3 box only added dark bars and height). The filters block holds: a titled "Time range" section with the date range slider, the earliest and latest dates of the data above its two edges and the selected range written under it, then a titled "Source" section with one row holding a checkbox on the left of each source (Sentinel-1, Sentinel-2; both on by default, so several can be selected).
- The reel is ordered by capture date and time, newest first: sorted on the `t` attribute, descending, with `id` as the tie-break, so the most recent entries are at the top. Above the entries, outside the scrolling area, is a small "Sort by" drop menu with two choices, Latest (the default) and Oldest (`t` ascending); it only changes the order of the list, not the map or the filters. The icons on the map are drawn in the same order: a `symbol-sort-key` of `t` for Latest or `-t` for Oldest (a higher key is drawn on top), changed with `setLayoutProperty` when the sort changes, so the entry at the top of the reel is the icon on top, and the selected pair is drawn above all. Icons use `icon-allow-overlap` and `icon-ignore-placement`, so none is hidden.
- An entry is a rounded card a little brighter than the layout, with white text, in two rows. Row one: a small pair icon (the same SVG, drawn through a CSS mask so one file serves both colours: yellow, red when sanctioned) turned 90° clockwise, so the hulls lie one above the other with the bows pointing left, and next to it the ID, a bit bigger and in medium weight. Row two, under both, smaller and in italic, laid out as three fixed columns (the area takes the rest and is cut with an ellipsis when long, the date has 3.75rem and the source 1rem, which leaves 81 px for the area at 1366 wide, enough for the longest name ("Johor East SCS", 80 px), right aligned) so the date and the source sit at the same place on every entry whatever the length of the area name: the area, then the capture date and the source (S1 or S2, the `source` attribute in capitals). The opened entry is bright cyan with dark blue text and a dark icon, so it stands out from the others. The reel and the details panel share one minimalist scrollbar (thin thumb in the map's blue, no arrows, transparent track), so all scrolling components look the same. A CSS mask only loads over http, not from a `file://` page, so the page has to be served to be checked. The ID shown, in the reel and in the panel header, is the published `id` (`<source>_<capture time>_<hull id>`) without its first two parts, that is everything after the second underscore without a leading `w<digits>-` scene prefix, for example `33113-13846` for `s1_20261022T224733_w0-33113-13846`; the prefix is dropped because it is not part of the hull number, and all 101 real IDs stay distinct without it; it is the same ID in both places. `hull_id` is no longer a column of the published Parquet, but it is part of `id` and so is public in every tile.
- The details panel has two fixed rows at the top that do not move when the content below scrolls (only the image and the grid scroll). The first is the "Capture details" title, styled like the active tab (no background, a 2 px `#4fd0e4` underline across the panel with the same side inset as the tabs row), which stays whether or not an entry is open and is level with the reel's tabs; the second, level with the reel's "Sort by" row, is the opened entry's own header in smaller type than the title (the pair icon at 1.25 rem, turned 90° like in the reel and red when sanctioned, the ID at 0.875 rem and, at the right end, a small close (x) button (a bright red cross, `#ff5c5c`, with a dark outline)). The reel and the panel are subgrids of the page grid (`body` has rows header, filters, tabs/title, sort/entry header, content, and both columns span the last three), so the rows line up whatever height the tabs take when their labels wrap; matching the title's padding to the tabs' makes its text sit level with theirs (checked in a browser at 1366x800: both rows have the same top and height in the reel and the panel, with and without an entry open). The type steps down with the hierarchy: the title 0.9375 rem, the entry ID 0.875 rem, the row labels and values 0.75 rem (they were 0.875 rem, which made the time and position look bigger than the ID), the registration line 0.6875 rem; the label column is 5.5 rem wide, which also stopped the capture time from overflowing its cell. The panel then holds then the capture image with a small muted caption under it ("Source: Sentinel-1" or "Source: Sentinel-2"; the source is not a row of the grid), then a grid with no column headers: a muted label on the left, the value on the right, with a border only under each row. Rows: the two vessels, each marked by its number in a small circle like the monitor app's (yellow when the vessel is known, that is it has a name; white with "N/A" when it is not), with each number immediately beside the vessel details; then name and a red "Sanctioned" label next to it when that vessel is sanctioned. When an IMO exists, Registration shows the IMO followed by the muted italic flag in parentheses; when only a flag exists, the flag is shown by itself. Then Capture time (date followed by UTC time) and Position (the exact `lat` and `lon` attributes, not the tile geometry, which at a low zoom is only accurate to about a kilometre). The panel content fits without scrolling at 1440x900, 1536x864 and 1920x1080 for a pair with a long name, and also at 1366x768 and 2560x1440; the image measures 154 px at 1366, 173 px at 1536, 216 px at 1920 and 288 px at 2560.
- Clicking an entry in the reel opens it in the details panel (one at a time), highlights it in the reel and, when the zoom is 10 or lower, flies the map to the pair or sanctioned vessel at zoom 11 (`FLY_ZOOM`; the tile source's last zoom is 14, so the map never overzooms its tiles). Above zoom 10 it does not fly, so a user who has already zoomed in keeps the view they have; a click on an icon on the map follows the same rule (`FLY_UP_TO_ZOOM`, `shouldFly` in `lib/geo.ts`, compared with the fractional zoom). Selecting a pair never changes the extent in any other case. Clicking a pair's icon on the map opens its entry in the details panel and scrolls the reel to it, with the same fly rule. The pair's icon on the map turns cyan (a third image, `pair-selected`, chosen by an `icon-image` expression that compares the pair `id` with the selected id) so it is easy to find; the other pairs keep yellow and red. The selection stays until the user picks another entry, presses the close button, switches tab, or applies a filter that excludes it. Panning or zooming away from it does not end it (it used to, and the panel emptying under a user who had only moved the map was jarring): the list follows the viewport, so the selected card is no longer in it, and the card is then pinned as the first card of the reel, whatever the sort, in a duller cyan (`#7aa3ad` against the `#4fd0e4` of a card in view) with a tooltip saying it is outside the current map view, the reel scrolls to the top so it is seen, and the details panel keeps showing it. Clicking the pinned card flies the map back to it (above the fly zoom too, keeping the zoom then, and for an open vessel it does not close the history, which a click on a card in view does); when the map returns to its area the card goes back to its place in the sorted list and its bright cyan. The pin starts only once the map has settled (`idle`, so the camera has stopped and the tiles have loaded) and the list has been rebuilt from it: after a click that flies, the list does not hold the entry until then and the card would flash grey, so a fixed wait was replaced by the map's own signal (`onSettled` from `MapView`, and `flyTo` returns whether it flew; a click that does not fly is settled at once, except when the tab changes, which always waits for the next `idle`). Close clears the selection (the panel is empty again, the icon returns to its colour) and does not move the map. There is no Show on map button.
- There is no Filter button: any change to the date slider or a source checkbox applies itself 300 ms after the last change, so dragging does not send a query per step. The first render never sends a query of its own.
- The only filters are the date range and the source. `sanctioned` is shown on the entry itself and is not a filter control.

## Solid 2
- The viewer moved from React 19 to Solid 2.0.3 on the `solid-2` branch. `vite-plugin-solid` is pinned to `3.0.0-next.27`: the `latest` tag (2.11) declares `solid-js ^1` as its peer and only the `next` line targets Solid 2. Bump it when a stable 3.x ships. `tsconfig.json` uses `jsx: preserve` with `jsxImportSource: "@solidjs/web"`, and `JSX` types come from `@solidjs/web`, not `solid-js`.
- The map is created in `onSettled` and not in the `ref` callback: a Solid ref runs before the element is in the document, and Mapbox measures its container when it is constructed. The `Map` goes into a signal (`map`) once it exists; every effect in `MapView.tsx` has `map()` in its compute function, so each one runs once when the map arrives and then on its own inputs. That replaces the `useRef` plus "latest props" ref of the React version, and the event listeners read `props.*` directly because nothing in a listener is a closure over an old render.
- Effects are `createEffect(compute, apply)`: what the apply step needs goes through the compute step. Re-reading a prop inside `apply` logs `STRICT_READ_UNTRACKED`. Where a value is deliberately not a dependency, it is read inside `untrack`: `queryStyle(props, id)` in the filter and tab effects of `MapView.tsx` (a filter change must not re-run on every tab or order change), `props.applied` in `Filters.tsx` (the comparison must see the latest applied filter without re-arming the 300 ms timer), the initial values of the two `Filters.tsx` signals (the slider and the checkboxes own their state after mount), and `update` in `lib/virtual.ts` (it is also the scroll handler).
- The fetch effects in `App.tsx` stay effects with an `AbortController` returned as cleanup, not async memos under `<Loading>`: the stale-response and "keep the old track while the new one loads" rules are explicit there and unchanged from the React version. They do not write `null` back when nothing is open. The memos that read `track`, `activityData` and `activityImoData` already ignore data that does not match the open IMO and the filter, and writing `null` from an effect made `EFFECT_RELAY_TEAR` fire (a derived `line` ran twice for one selection change).
- `Details.tsx` renders the entry body inside `<Show when={props.entry} keyed>`, so the body is rebuilt per selected entry, the same lifetime the React `key={entry.id}` gave the capture image (its "failed" flag starts fresh). Lists that need stable rows use `<For keyed={(row) => row.id}>`, so an entry rebuilt with a new object but the same id keeps its DOM row; `Reel.tsx` depends on this because `decorated` in `App.tsx` copies the sanctioned entries.
- Range sliders and the sort select listen to `input`/`change` natively: `RangeSlider.tsx` uses `onInput` where React's `onChange` fired on every move.
- `App.tsx` passes a memo for every prop that is not a plain signal read (`activityFocus`, `pickedId`, `cardId`, `heads`, the track and history), because effects never compare: a prop that is an inline expression would re-run its effects on every change of anything it reads.
- Setters do not update reads until the flush. Handlers in `App.tsx` read `selection()` and `viewEntries()` before they write, as the React ones read their refs first, and the tour captures `index()` and `multi()` at the start of `next` the way the React closure did.
- Checked in headless Chromium (software WebGL) against the dev server and the local service, with the `main` React build run next to it for comparison: the week's list, widening the range, selecting a card (the map flies, the details and the cyan icon follow), sorting, unchecking a source, the hover popup and a click on a map icon, the tour up to the sanctioned step, and a vessel opened from a pair with its previous positions, a picked position, the related activity and the back link. Every step gave the same state in both builds and the rendered side panels differ only in attribute order. The local service had no sanctioned tiles or index, so the sanctioned list itself was not exercised: for the vessel flow one vessel was marked sanctioned with a real IMO in a temporary local patch, since removed.

## Tabs
- The reel has two tabs at its top, Suspicious activity (the first, the pairs) and Sanctioned vessels, above the sort bar. The tab is app state (`App.tsx`); the filters (date range, source) and the sort are shared by both tabs and survive a switch.
- A manual tab switch clears the selection (the details panel closes and the cyan icon goes) and empties the list at once; the list is then rebuilt from the map's rendered features of the new tab's layer (`signature` is reset so the same set of IDs is not skipped). The reel scrolls back to the top. Header navigation between a suspicious activity and its sanctioned vessel switches tabs while saving the immediately prior detail and its map target for the one-level back link.
- Each tab shows one query at a time (`TabQuery` in `queryLayers.ts`): a vector source and a symbol layer whose tile URL carries the whole query (date range and sources), ids `pairs:0`, `pairs:1`, and so on. The tile layer name stays `pairs` and `sanctioned`. A switch of tab only changes layer visibility; the hidden layer's source loads no tiles (checked in a browser: after a switch only the new tab's tiles were requested).
- A change of the range or the sources never changes a layer that is on screen. The layer for the new query is added on top of the old one, and the old one is removed only when the new source has loaded tiles (`sourcedata` of type `content`) and the map is idle (`idle` also waits for the icons' fade-in, so the old layer is still fully drawn while the new icons appear, and nothing dips). The icons that stay are drawn by the new layer from the same positions as by the old one. This was chosen over a delta of tiles with layer filters, which saved downloads but rebuilt layers in place and was much more code; the price is that every change downloads the visible tiles of the new query again, about 4 requests for the viewport in the test below. If the query changes again before the swap, the half-loaded layer is dropped and the old one stays up; if the new tiles fail (`error` on the source) or take more than `SWAP_TIMEOUT_MS`, the old query stays. A tab that is not shown swaps at once because it loads no tiles. While both layers draw, the reel, hover and click read only the layer on show, and `onSwap` makes the map read the reel again after the swap. Since the tiles are exactly the query, a pairs layer has no filter, and a newly discovered area is requested for the latest query only (checked in a browser: after a range change and after a source change, panning to a new area requested only the new query).
- Checked in a real browser (Chromium, WebGL in software, the dev server on synthetic data: five pairs in one area, a move of the range that drops two and adds two): with the swap, the three icons that stay show no change in their pixels at any captured frame (at most 2 of 765, the double-drawn antialiased edge while the layers overlap); the same scenario on the version that called `setTiles` makes the three icons disappear for two frames, and the check of icon ids in `queryRenderedFeatures` did not see that, so only the pixels of the screen count as a test. The dropped icons disappear when the old layer is removed, and the new ones fade in while the old layer is still there. The same holds for the source switch, for widening, and for the sanctioned tab.
- The sanctioned layer cannot be filtered by time alone, because a vessel is one icon, its newest detection under the filters, and a layer filter cannot group. Its tiles therefore hold every detection of the query, and `/sanctioned-index` gives the viewer a compact list of all detections (`id`, `imo`, `t`, `source`), fetched once. `latestPerVessel` in `heads.ts` picks the newest detection per vessel inside the range and sources (ties go to the lower ID, as the server did) and counts the rest for the "×N" badge; the layer filter is then `id in heads`. The layer of a new query gets the heads of that query when it is created and keeps them (`id in heads`); a change of the heads alone, which happens once when the index arrives, updates only the layer of the current query, never the one still on show. A vessel whose newest detections leave the range moves back to the newest one that is left, and one with none left disappears. The activity overlay tile is keyed only by the finding ID for the same reason.
- A sanctioned vessel is one hull (`vessel-sanctioned` red, `vessel-selected` cyan, drawn by `vesselSvg` from the same hull path as the pair, at half the width, bow up at yaw 0). The images are registered next to the pair images in `addMapImages`. In the reel, popup and details header the icon is `sts-vessel.svg` through the same CSS mask as the pair, a wider hull than the map's so that it reads at 1.5 rem, always red.
- A sanctioned vessel's details panel is titled with the vessel's name and has, instead of the pair's numbered vessel rows (the 1/2 markers are for the two hulls the capture marks), an ID row (the short ID the pairs show as their title), a Registration row with the IMO followed by the muted, smaller, italic flag in parentheses when an IMO exists, or a Flag row when only the flag exists (the Sanctioned badge is left out because the whole tab is sanctioned), then Capture time (date followed by UTC time) and Position. Area is omitted because it is already on the entry. A sanctioned vessel's entry (reel card, hover popup and details header) is titled with the vessel's name instead of the short ID (`entryTitle`); a vessel without a name falls back to the ID. Pairs keep the short ID.
- A sanctioned vessel with an IMO has a related suspicious-activity list in its details panel. `/activities/<imo>` matches the IMO exactly against either participant of each pair finding, applies the selected date range and ignores source checkboxes. Each list row has a small yellow pair icon and ID, then the area and capture time. A small yellow pair icon also appears on vessel cards when that vessel has at least one match in the selected date range; it sits immediately left of the detection-count badge. `/activity-imos` supplies that availability set once per date range. The activity list has its own 12 rem maximum height and scrolls independently. Selecting a row keeps the sanctioned vessel selected in the reel and on the map, and adds the selected finding from `/tiles/activity/{z}/{x}/{y}.mvt` as a yellow, unselected temporary MVT overlay; its URL carries the exact activity ID and date range and omits source filters. The details show the normal activity fields and header `<vessel name>/<activity ID>`; only the vessel name is clickable and restores the saved vessel detail. A sanctioned participant name in an activity detail opens that IMO's `/tracks/<imo>` history, switches to the sanctioned-vessel tab and shows its current filtered vessel detail with previous positions and the existing history style. That view uses `<activity ID>/<vessel name>` in the header, with only the activity ID clickable to return to the exact activity state. Returning from either direction restores the prior tab, map focus and detail; the existing camera rule applies on each transition. Closing the activity detail removes its temporary MVT source and layer.
- One vessel is one icon on the map and one card in the reel: its newest detection under the current filters (the tile carries only that one, see pipeline.md). The card shows a "×N" badge when the vessel has N detections under the filters (N includes the card's own; no badge for one). Clicking the card, or the icon on the map, selects it (cyan) and opens its history: the other detections come from `/tracks/<imo>` (fetched when the history opens, aborted when the selection or filter changes, a failed request just shows nothing) and appear in three places at once, all cleared together when the history closes or the selection goes: as icons on the map (a GeoJSON source and layer, `history`, under the cyan one) in a lighter red, `#e88f8f` against the `#d64545` of a newest detection, so they look older, as a dashed white line (`TRACK_LINE`, 2 px, dash 2-2) through every detection from the newest to the oldest, and as a list under the card.
- The history list is a box attached under the open card (the card's bottom corners are squared) whose height follows its rows (1.75 rem each plus 0.5 rem padding, `historyHeight`) up to three rows (5.75 rem); with more than three rows the box is half a row taller (`HISTORY_PEEK_REM`, 0.625 rem, which with the box padding shows half of it) so the fourth row shows its top half and says the list scrolls, and it scrolls, with a 0.1875 rem grey scrollbar thumb. While the list is loading the height is taken from the card's count. A row is the vessel icon in the same lighter red, the area, the date and the source in an even 0.75 rem grid, no name (it is the same vessel). The reel's rows below the open card move down by the box height: the virtual list takes one `Gap` (index and height) into its range, offset and reveal maths (`lib/virtual.ts`). Only one history is open at a time. Clicking the selected card again closes the history and keeps the selection; clicking the card of an open vessel while one of its history rows is picked selects the card again.
- Picking a history row, or a revealed icon on the map, shows that detection in the details panel and flies to it (always, even above the fly zoom, keeping the zoom then, so a detection outside the view is brought in). Clicking the picked row again (or its grey icon on the map) un-picks it: only the card stays selected, the details panel shows the vessel's newest detection again, and the map flies back to it when it is out of the view (above the fly zoom too, as for a pinned card) and otherwise follows the usual fly rule. The card stays cyan, the row gets a grey background (its icon stays the lighter red) and the picked icon on the map turns grey (`vessel-picked`). While a history is open its card stays in the reel, pinned first in the duller cyan, when the map has moved away from the vessel's newest detection (the fly to an older one usually does), so the list stays and the next row can be picked; a click on that card flies to the newest detection even above the fly zoom, since it is not in the view. A picked detection is not dropped when the map leaves it, and neither is a selected card; only a close, another selection, a filter that excludes it or a tab switch clears it. The reveal covers the vessel under the current filters, not the viewport, so a vessel seen in two hot spots gets a straight line between them (Mapbox draws lines straight in Mercator, not along the great circle). The vessel is identified by its IMO (7 digits on every sanctioned row at the time of writing). A sanctioned vessel can also be opened from its name in a suspicious-activity detail; this follows the same per-IMO history query and styling.

## Map
- Hovering a pair's icon on the map shows a Mapbox GL `Popup` (no close button, closed on mouse leave, anchored above the icon with a small offset). Its content is the same card markup as a reel entry (icon, ID, then area, date and source), so it gets the same colours, fonts and structure: the popup uses the card background (`#223c4e`), white text and rounded corners, and the tip has the same colour. The look is a CSS override of `.mapboxgl-popup-content` and `.mapboxgl-popup-tip`; the page draws the popup with the DOM MapLibre generates (`mapboxgl-popup`, `-anchor-bottom`, `-tip`, `-content`). The cursor is a pointer over an icon. Icons are small at low zoom and grow only slightly with it, so they are never huge: `icon-size` is an interpolation on the zoom, starting at 0.3 of the drawing at zoom 4 and below, 0.5 at zoom 10, 0.8 at zoom 14 and 1 at zoom 16 and above (the starting values, to be tuned on the real map).
- The list is always built from the features in the current viewport (every vessel or pair in it) and is never locked, at any zoom. After flying to a vessel the list therefore shows only what is in that small viewport; the user pans and zooms freely at every zoom. There is no Back to query area button: it was dropped together with the stored query area and the zoom threshold 13 it used.
- Basemap: a Mapbox style drawn by Mapbox GL JS, always with the Standard `lightPreset` set to `dawn` (`STYLE_CONFIG` in `lib/mapbox.ts`, chosen because it reads best behind the icons; the config is ignored by styles that are not Standard), with the public token as `accessToken`. The style is `VITE_MAPBOX_STYLE` (a `mapbox://styles/<account>/<id>` address or `<account>/<id>`), and when it is not set the Navigation Night style `mapbox/navigation-night-v1` is used (`lib/mapbox.ts`). The token is a public one (`pk.`), which the browser can see by design, so only a public token is ever used, never a secret one (`sk.`), and it should be restricted to the viewer's address in the Mapbox account. Nothing credential-like or account-specific is committed: the token is `MAPBOX_ACCESS_TOKEN` and the style is `MAPBOX_STYLE` in the git-ignored `deploy/deploy.env` (`deploy.sh` and `compose.yaml` hand them to the image build as `VITE_MAPBOX_TOKEN` and `VITE_MAPBOX_STYLE`), and `VITE_MAPBOX_TOKEN` and `VITE_MAPBOX_STYLE` in the git-ignored `frontend/.env.local` for local work; the repo holds only placeholders, and the built `frontend/dist` and the image, which contain both, must not be published. Mapbox GL JS bills per map load under Mapbox's terms, and visitors' requests, including their IP addresses, go to Mapbox. Without a token the viewer shows a plain background (the style address is only built when there is a token). If the style fails to load the viewer shows a toast and falls back to the plain background. The Mapbox and OpenStreetMap attribution and the Mapbox logo are shown. The icons carry outlines so they read on any basemap.
- Rotation and tilt are blocked (drag and touch rotation off, keyboard rotation off, `maxPitch` 0). The map is not enabled for touch: the viewer is for a mouse and keyboard, so the hover popup needs no touch variant.
- Map controls stay, restyled in the dark theme: the navigation control with zoom in and out (no compass, since rotation is off), the scale bar at the bottom left and the attribution at the bottom right.
- When the filter changes, a selected pair whose `date` or `source` falls outside the new filter is dropped: the details panel closes and the cyan icon goes. The viewer can decide this from the selected pair's own attributes, without querying.
- Errors (a tile request or `/metadata` failing) show in a toast at the top centre of the map, in the dark theme with a red accent and a close (x) button, and go away by themselves after a few seconds.
- The fly rule compares `map.getZoom()` as it is, fractional: flying to zoom 11, and only up to zoom 10 (see Layout and the reel).
- Tile layers `pairs` and `sanctioned` (see Tabs), one point per finding; there are no `links` layers. The viewer draws a two-vessel icon at the pair position: two identical silhouette hulls side by side, a pointed bow and a blunt stern like the ships in the capture image, drawn at yaw 0 with both bows pointing south (`frontend/src/assets/icons/sts-pair.svg`). The map rotates it with `icon-rotate: ["get", "yaw"]` and `icon-rotation-alignment: map`, so the angle is measured from north.
- The icon is not a fixed file: the frontend has an SVG creator function that takes parameters such as the colour and the base orientation and returns the SVG for them. A symbol layer cannot use an SVG directly, so when the map loads the viewer builds one image per colour (the SVG through an `Image` with explicit size, at 2x or 3x pixel ratio) and registers each with `map.addImage`; nothing is redrawn while the viewer runs. There are three colours, and a colour applies to both hulls of a pair: yellow (`#f2c230`, blue was dropped because it is too close to the ocean colour) when sanctioned is false or unknown, red (`#d64545`) when either vessel is sanctioned, i.e. when the tile attribute `sanctioned` is true. The style picks the image with `icon-image: ["case", ["get", "sanctioned"], "pair-sanctioned", "pair"]`. Per-pair rotation is not done by redrawing: it stays in the style, driven by `yaw`. On the map the icons carry an outline so they stay visible on any basemap: black around yellow and red, and a ring of two strokes around the selected pair and vessel (cyan `#4fd0e4`, the images `pair-selected` and `vessel-selected`) and the picked detection (grey, `vessel-picked`): a white stroke 12 units wide (6 show outside the hull) inside a black one that reaches 3 units further out, drawn at 1.4 times the size of the other icons. At 8 and 2 the white and the black read as the same width at the map's small icon sizes, so the white is twice the black now. The hulls of a pair are 8 units apart, less than the two white rings need, so each white ring is cut at the middle (a clip path per hull, 3 units either side of the centre line) and the black layer under them shows through as a black line between the hulls as wide as the outer one, with a thinner white strip on each side of it. The first version, cyan with a white outline only, all but vanished on the light sea of the basemap, because the other icons have black outlines and the white blended into it; the black outer stroke is what separates the ring from any background, the white keeps it readable next to the black outlines of its neighbours. The creator takes the fill, the stroke and optionally the outline, its width and a scale as parameters; the view box grows with the ring so it is not cut off, and `rasterPair` and `rasterVessel` size the image to match. The icons in the reel and the details panel have no outline.
- The hot-spot boundaries are white lines (2 px, full opacity) and the pair icons are drawn on the `top` slot with an emissive strength of 1. The custom style has lights and a Standard import, which darken and bury layers that have no slot or emissive strength: the lines used to show as a faint grey. There is no animation when a query adds or removes pairs: fades were tried (the whole layer, then only the pairs that differ between the old and the new filter) and dropped, because the icons then appeared and disappeared later than the data.
- The hot-spot areas are drawn at every zoom as white boundaries with their names, with no fill logic or counts, whether or not they hold data. They are not bundled: the viewer fetches them from `/hot-spots` at start (`fetchHotSpots`) and creates the map only once the list has arrived. If the request fails a toast says so and the map shows no areas and keeps the default start view.
- The areas have one source of truth, the monitor's published hot-spot list, which the pipeline fetches and serves (see "Hot spots" in [pipeline.md](../../pipeline/context/pipeline.md)); this repo holds no copy of the boxes or the labels. Each area carries a one-word `label` ("Fujairah", "Sohar", "Sikka", "Johor", "EOPL"), which the viewer shows everywhere it names an area: the map, the cards, the hover popup, the history rows and the related-activity list. The names are code names ("Johor East SCS", "Malaysia EOPL") and too long for a card. The viewer keeps the labels from the `/hot-spots` reply in a lookup (`setHotSpotLabels`, `hotSpotLabel` in `lib/entries.ts`) and, for an area name it does not know, shows the name in title case. The earlier hand-edited copy in this repo had its own boxes, widened by hand for two findings; the monitor's list has since been widened too (Malaysia EOPL 103.0°E to 106.5°E and 0.3°N to 1.8°N, Johor East SCS 103.5°E to 106.5°E and 1.8°N to 3.3°N), so those findings lie inside their areas.
- Start view: the viewer fits the boxes of all the areas in the list with padding for the reel, capped at zoom 4, so that all of them are visible whatever the screen width. Sikka lies between Sohar and Johor, so adding it did not change the fit. A fixed zoom 4 centred at about 81.1°E, 13.3°N only shows all of them when the map area is about 1250 px wide, which with a reel of about 450 px needs a window wider than about 1700 px.
- Dates are UTC everywhere, including the default range at start and the slider labels. They are shown as `DD.MM.YYYY` (for example `01.09.2026`); the `date` tile attribute and the filter parameters stay `YYYY-MM-DD`.
- There is no clustering for now. The tiles carry every finding at every zoom and the map draws all of them, with no limit and no hiding; if the map gets cluttered, narrowing the filters is the user's job. Clustering is parked, not dropped: it still makes sense and needs refining before it is built. The idea, as far as it was designed: the viewer groups the pairs in view into clusters in the list only (never in the MVT), each tied to an area it draws as a GeoJSON polygon; below zoom 10 the four hot-spot areas, at zoom 10 to 13 four quadrants (NE, SE, SW, NW) cut from the centre of a hot spot, from zoom 14 circles named A, B, C from west to east, each level shown only above a threshold of 20 pairs on the display; clicking a cluster flies to its area. The full wording is in this file at commit `184f24c`.

## What the service gives the viewer
- Where the map's data comes from: the map draws vector tiles (MVT, Mapbox Vector Tiles), small binary files that hold the features of one square of the map at one zoom level, addressed as `/tiles/{z}/{x}/{y}.mvt`. Nobody builds them ahead of time. The service cuts each tile on request from `findings.parquet` (or `sanctioned.parquet`) with one DuckDB query (`ST_AsMVT`), applying the date range and sources that the viewer puts in the tile URL, so a change of the filters is a new URL and new tiles. A tile carries every attribute the list and the details panel show, so the viewer needs no other endpoint for them. How the tiles are cut, their attributes, the filters and `/metadata` are described in [pipeline/context/pipeline.md](../../pipeline/context/pipeline.md), section serve.py.
- The legend is a small fixed box in the map's bottom-left corner (`components/Legend.tsx`), always visible, lifted 4.25 rem so it clears the scale bar, which sits above the Mapbox logo. It follows the tab because the tabs draw different symbols, and it is deliberately minimal (the first version listed nine rows and was too big). Suspicious activity: "Suspected STS" (yellow) and "Suspected STS with sanctioned vessel" (red) and "Selected" (cyan), all pair icons. Sanctioned vessels: "Sanctioned vessel" (red), "Selected vessel" (cyan), "Previous position" (light red) and "Selected previous position" (grey), drawn from `VESSEL_IMAGES` with the same SVG builders as the map. The path and the hot-spot outline are left out on purpose, and the word "pair" is not used in the UI. A new map symbol needs a row here.

- A `font: inherit` shorthand written after `font-size` in the same rule silently resets the size: `.history-item` did this and showed its rows at 1 rem instead of 0.75 rem, which cut the area name ("S...") in the narrow reel. The size now comes after the shorthand.

## Tour.tsx
- Guided tour, mounted under `npm run dev` and in any build made with `VITE_TOUR=1` (a build arg in the `Dockerfile`, passed by `compose.yaml`, empty by default), on every page load; the image `deploy.sh` ships is built without it, so the live site has no tour. Remembering that a visitor has seen it (localStorage) and a way to start it on demand are not built yet.
- Ten steps, each with its own text in `STEPS`: purpose, all hot spots, the detections list, a selected detection (its details and its icon on the map are highlighted together, one step), then the sanctioned vessels (the tab; one vessel with its details and its icon on the map highlighted together, one step) and then the filters (one step for both, then one each for the time range and the sources) and a closing step. "Next" on the hot spots flies to `TOUR_HOT_SPOT` (`fujairah_outer`, in `lib/constants.ts`, looked up by name in the published list) with no highlight and no card of its own: the zoom only brings the vessels and the reel into view. If that area is missing, or has no findings in view after 6 s, the tour goes straight to the time range.
- Sanctioned part: "Next" on the selected detection switches to the sanctioned tab (`changeTab`) and fits the hot spot again, so the "Sanctioned vessels" step shows the whole area with the reel (the tabs and the list of vessels) highlighted. "Select a vessel" there picks the first vessel in view, preferring one in the tour's hot spot, and selects it like a map click; the next step highlights the details panel and the vessel's icon on the map, the same way as for a detection (`picked` holds the entry whose position is projected). There is no step for a vessel's earlier positions or its track any more (an earlier version picked the newest previous position and fitted the map to the track; dropped as too long). If no vessel is in view the tour goes back to the suspicious activity tab and on to the filters.
- Filters part: "Next" on the track step switches back to the suspicious activity tab (`changeTab("pairs")`, which clears the selection) and fits the tour's hot spot again, with no step of its own for the switch. The filters step highlights the whole filter panel as one box (`data-tour="filters"`); the time range and sources steps highlight their own field (`data-tour="time-range"`, `data-tour="sources"`), and its button "Change the time range" hides the card, waits `SLIDE_DELAY_MS` and then moves the slider's start thumb back `WIDER_RANGE_DAYS` (30) days from the current end date (clamped to the first date in the data) over `SLIDE_MS` with an eased curve, through `FiltersHandle.slide` (App passes it to the tour as `onSlide`). Only the slider is animated; the filter is applied once by the component's own debounce after the thumb stops, so the map reloads once, not on every day, and the tour moves on when the applied filter has caught up (no step shows the result; the new range is visible behind the sources step). Widening, not narrowing, because the newest days can hold no data (the data ends before today), which would show an empty map; if the range already covers the data nothing is changed. The sources step only explains the two satellites; an earlier version turned one off and on again and was dropped as too long. "Next" there runs the reset (`resetView`: suspicious activity tab, the original filter, all hot spots in view), so the closing step, with no highlight, is centred over the starting view; it has "Done" and no Skip. The sanctioned part's fallbacks (no vessels in view, a vessel with no earlier positions) also go through the switch back before the filters step.
- Leaving the tour early (Skip, Escape) runs the same reset, restoring the filter it started with (`startFilter`, captured when the tour mounts) as well as the tab and the map; at the closing step it has already run (`restored`). `Filters.tsx` follows `applied` from outside (a second effect writes the slider and the sources when the applied filter differs from the one the component itself last sent), otherwise the slider would stay where it was while the map changed.
- Wording: step titles, texts and buttons use the data's own terms (detection, vessel, position), never the UI element ("card"): the tour is how a visitor learns what the data is, so the buttons read "Select a detection", "Select a previous position". A button names its action only when the click does something visible (selects an item, changes the range or a source, zooms); a step that only explains has "Next".
- Leaving the tour, by Finish, Skip or Escape, resets the view: `changeTab("pairs")` (back to Suspicious activity, selection cleared) and the map fits all hot spots at the opening framing (padding 48 px, max zoom `START_MAX_ZOOM`).
- No library. An SVG mask dims the page with one hole per target and a cyan outline; the card sits above it. Map targets are projected: every vertex of a hot-spot polygon goes through `map.project` (plus the map container's offset, via `MapHandle.project`) and the bounding box is padded 8 px with a 56 px minimum side, so the small hot spots stay visible. Each box also takes in the area's label (the `.hot-spot-label` marker, found by its text), which sits above the polygon. The selected STS is one projected point given the same minimum box. Panel targets are not padded: the outline sits 1 px inside the panel's own edge so it never spills over the neighbouring column (padding them 8 px did). Panels carry `data-tour` attributes (`map`, `reel`, `details`, `time-range`, `sources`).
- `placeCard` (`lib/tour.ts`, tested) scans a 16 px grid for the position with no overlap with any target (16 px clear) nearest the targets' centre; for map steps the search area is the map, otherwise the window. That keeps the card off every hot spot at the overview. If nothing is clear it takes the least overlap.
- The card picked for "Capture details" is the middle of the Fujairah entries in view, not of the whole list: Sohar overlaps the Fujairah view and the first version picked a Sohar card. It goes through the same `select` as a click on the map, so the reel scrolls to it and the map flies to it.
- `MapHandle.whenSettled` waits for the map's `idle`, capped at 5 s: in a headless browser with software rendering `idle` was unreliable and the tour never started.
- The overlay is hidden during map flights. Enter or the right arrow goes on, Escape skips.
